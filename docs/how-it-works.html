How it works

The Ring process hosts the .NET runtime and talks to it through a small managed bridge. This page explains the pieces, so the rest of the documentation makes sense.

The layers#

The extension and the bridge#

ring_dotnet.dll is a normal Ring extension written in C. When the first .NET call is made it:

  1. finds the installed .NET runtime and starts it inside the Ring process with hostfxr (no separate process, no IPC),
  2. loads RingDotNet.Bridge.dll, a small C# assembly,
  3. keeps one entry point: dotnet_request(operation, data).

The bridge uses reflection. A Ring call such as oSB.Append(", ") becomes a request call [handle, "Append", ", "]; the bridge finds the right overload from the argument types, invokes it, and returns the result.

Handles#

.NET objects never leave .NET. Ring holds a handle (a number) inside a DotNetObject, and the bridge keeps the real object in a table. The generated wrapper classes are DotNetObjects with typed methods, so oSB.Append(...) and oSB.callMethod("Append",[...]) do the same thing.

The wire format#

Values travel as a compact tagged text: s5:Hello (string), n2:42 (number), l... (list), o3:17 (object handle), c... (callback), e... (error). Numbers that are not whole travel as the 8 bytes of the double, so there is no loss of precision. Binary data (byte[]) travels as a Ring string.

Generated wrapper classes#

tools/gendotnet.ring reads the manifest (tools/dotnetmanifest.ring) and uses reflection to write one Ring class per .NET class into libraries/dotnetlib/generated/. These files are plain Ring source with real inheritance, properties (as attributes with getX/setX), events and enums. dnImport("System.IO") loads one namespace on demand. A class index lets the library import the right namespace automatically when a returned object has a type that is not loaded yet.

Results are wrapped by their real type#

When a method returns an object, the bridge sends the list of its type and base types. dnWrapObject looks for the most specific generated class (importing its namespace if needed) and creates it. If no class exists the result is a plain DotNetObject — use callMethod and getProp on it.

Callbacks: Ring code called from .NET#

dnCallback("...") passes Ring code where .NET expects a delegate. The bridge builds a delegate of the exact type with a compiled expression; when .NET invokes it, the C extension runs the Ring function on the Ring thread and returns its result. Callbacks run synchronously during a call, which is why events from timers on other threads are ignored (see Gotchas).

Threads#

ThreadWhat runs there
The Ring threadAll Ring code, all calls into .NET and all callbacks. With dnUseDesktop() it is an STA thread and runs the message loop in Application.Run().
.NET threadsKestrel connections, tasks, timers. They never call Ring directly. The web server queues requests and Ring handles them in serveOne().

Runtime modes#

The runtime is configured with one of four runtimeconfig.json files: base (RingDotNet.Bridge), desktop (RingDotNet.Desktop), web (RingDotNet.Web) and all (RingDotNet.All). dnUseDesktop(), dnUseWeb() and dnUseAll() select the file before the runtime starts. dnUseData() only loads the Entity Framework assemblies; an AssemblyResolve handler in the bridge finds them next to it.
